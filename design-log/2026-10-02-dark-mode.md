# Dark mode (surface elevation, re-derived accents)

**Date:** 2026-10-02
**Status:** accepted
**Author:** collaborative

## Context

[2026-10-01-agora-pos-color-system](./2026-10-01-agora-pos-color-system.md) removed the old dark theme and noted that bringing it back means adding a `.dark` token block and a toggle. This entry does that and supersedes only that part of the earlier entry. The light palette and all light-mode decisions there still stand.

The ask: dark mode must not be "light UI with dark backgrounds". Contrast has to be reviewed per pairing and the visual hierarchy has to survive the inversion.

## Decision

### Mechanism

- `.dark` class on `<html>`. The class is set before first paint by an inline boot script (`ThemeBoot.astro`) that reads `localStorage["agora-theme"]` (`light | dark`), and falls back to `prefers-color-scheme` when nothing is stored ("System").
- `ThemeToggle` (Light / Dark / System menu) lives in the dashboard topbar and the customer layout header. Auth pages follow the stored or system preference but have no toggle.
- Components keep using the semantic tokens. Dark is a second value set for the same names, so no component needs a `dark:` variant except for a few overlay cases.
- `theme-color` meta is updated by the boot script and the toggle.

### Hierarchy: elevation by lightness, not by shadow

Shadows are invisible on dark, so each step up in importance is a lighter surface plus a visible hairline border.

| Role | Light | Dark |
| --- | --- | --- |
| `--canvas` (page behind everything) | `#f5f5f5` | `#0e0f11` |
| `--card` / `--background` / sidebar | `#ffffff` | `#1a1d21` |
| `--popover` (menus, dialogs, tooltips) | `#ffffff` | `#21252a` |
| `--muted` / table header / row hover | `#f5f5f5` | `#252a30` |
| `--accent` (hover on a popover) | `#f5f5f5` | `#2d333a` |
| `--border` | `#cccccc` | `#343a42` |

Dialogs and alert dialogs switch from `bg-background` to `bg-popover` so they sit above the page. Overlay scrim is stronger in dark (`black/70`) because black/50 on a near-black page barely separates.

Text ladder: `--foreground` `#ececee` (not pure white, avoids glare and halation), `--muted-foreground` `#a9aeb7`.

### Accents are re-derived, not inverted

Saturated mid-tones that work on white look heavy or vibrate on dark. The same single-CTA rule applies (red = action, teal = information), using the lighter palette members:

- `--primary` becomes `primary-200` `#ff6366`. Foreground is the dark surface color, so the button is coral with dark text. The same token is also used for `text-primary` links and icons, which is why a single value has to pass both jobs. Hover brightens (mix with white) instead of darkening.
- `--operational` becomes `accent-100` `#25b1bf` with dark foreground (accent-200 `#005461` is only about 2:1 on the dark card).
- Selected rows and `--primary-subtle` become a deep red tint of the surface (`primary-100` at 26% over the card) instead of the pale pink `primary-300`.
- Status colors get lighter text-safe values and dark tinted `soft` backgrounds with light `ink`. Fill buttons and badges (destructive) use a new `*-foreground` token (dark surface in dark mode, white in light) instead of hardcoded `text-white`.
- Chart series are re-picked so each is at least 3:1 against the card.

### Verified contrast (WCAG, dark)

| Pair | Ratio |
| --- | --- |
| foreground on card / popover / muted | 14.9 / 13.7 / 13.0 |
| muted-foreground on card / muted | 7.9 / 6.9 |
| primary as text on card / popover | 6.1 / 5.6 |
| dark foreground on primary / primary-hover | 6.0 / 6.7 |
| primary on primary-subtle | 4.8 |
| operational as text on card, dark on operational | 6.8, 6.7 |
| success / warning / error as text on card | 7.6 / 8.6 / 7.0 |
| success / warning / error ink on their soft | 8.9 / 8.7 / 8.0 |
| input border on card | at least 3:1 |
| chart series on card | at least 3:1 |

(Values computed with the WCAG relative-luminance formula against the first-pass surfaces; the final surfaces are slightly lighter, which only raises light-on-dark ratios.)

### Intentional exceptions

- QR code containers stay white (scanners need dark-on-light).
- Photo overlays (carousel dots, "view" chips) stay white on black scrims.

## Alternatives Considered

- **Invert the light tokens** (swap bg and text only). Rejected: red `#de283b` as text on dark is about 3.6:1, teal `#005461` is unreadable, and shadow-based elevation disappears, which is the "plain dark background" outcome the user wanted to avoid.
- **Separate `--primary` (fill) and `--primary-ink` (text) tokens.** Cleaner in theory but touches about 70 `text-primary` usages in 23 files, including `hover:` and arbitrary-variant usages that a CSS override cannot catch. A single coral value passes both roles at 5.6 to 6.1:1, so one token is enough.
- **Pure black canvas.** Rejected: harsh against bright accents and loses a step of elevation.
- **Follow OS only, no toggle.** Rejected: POS terminals often run in rooms where the OS setting is not what the operator wants.

## Consequences

- The brand button reads coral-with-dark-text in dark mode, a deliberate departure from white-on-red. Brand red `primary-100` is still used for the selected-row tint and chart series 7.
- Any new component must use semantic tokens; hardcoded `bg-white`, `text-white`, or hex colors will look wrong in one theme.
- Tokens are defined in `src/styles/global.css` (`:root.dark`). Auth backdrop scrim, shadows, and the selected-row tint no longer derive from `--text-100`, which flips with the theme.
